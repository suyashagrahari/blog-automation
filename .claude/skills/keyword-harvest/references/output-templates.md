# Output templates

Use these structures exactly. Consistency across runs is what makes the output
comparable over time — and comparability is what lets the user see whether their SEO
is actually improving.

All four files live in `content/keywords/<YYYY-MM-DD>-<seed-slug>/`.

---

## 1. `keyword-inventory.csv`

One row per extracted keyword. Header:

```
keyword,cluster_id,source_url,source_domain,evidence_type,intent,page_type_required,est_volume,volume_source,weakness_count,gate_failed,bucket,priority_score,ranking_urls,category
```

**Field definitions:**

| Field | Values |
|---|---|
| `cluster_id` | `C01`, `C02`… Keywords sharing a cluster share an ID. |
| `source_url` | The exact URL the keyword was extracted from. Required. For generated candidates, `GENERATED`. |
| `evidence_type` | `TARGETED` (competitor built for it) / `TARGETED+CONFIRMED` (built for it *and* ranks top 10) / `PAA` / `RELATED_SEARCH` / `LLM_CITED` / `GENERATED` |
| `intent` | `transactional` / `commercial` / `informational` / `navigational` |
| `page_type_required` | `tool` / `blog` / `listicle` / `comparison` / `hub` |
| `est_volume` | A band, e.g. `200-600`. Never a single invented figure. |
| `volume_source` | `TOOL` or `EST` |
| `weakness_count` | 0-10 from Gate 4 |
| `gate_failed` | Blank if it survived; otherwise `G1`…`G6` |
| `bucket` | `winnable` / `medium` / `do-not-attempt` |
| `priority_score` | winnability × intent fit × volume band |
| `ranking_urls` | The live top 3 URLs, **pipe-separated, in position order**. This is the "who currently ranks" column and it is what a reviewer reads first. |
| `category` | Functional core category for the studio sheet (e.g. `birthday`, `festival`, `apology`). Optional; falls back to the cluster's primary keyword. |

The last two columns are extensions beyond the base spec. They exist because the
Excel sheet in Phase 10 is the artifact people actually work from, and a sheet that
names the keyword without naming the incumbent is half a deliverable.

**Quoting:** any field containing a comma, quote, or newline must be double-quoted
with internal quotes doubled (`""`). `ranking_urls` frequently contains commas in
tracking parameters — strip query strings from the URLs before writing them.

Include failed keywords with their `gate_failed` value. Showing what was cut and why
is what makes the surviving list trustworthy.

## 2. `shortlist.md`

Exactly 15 clusters, ranked. For each:

```markdown
### N. [primary keyword]

- **Bucket:** winnable / medium
- **Est. volume:** [band] (EST or TOOL)
- **Intent:** [type] — searcher's job is [reading / building / comparing / buying]
- **Currently ranking:** [pos 1 URL], [pos 2 URL], [pos 3 URL]
- **Why winnable:** [name the actual weak results — "positions 3, 6 and 8 are Reddit
  threads; position 5 is a 2019 page with dead links"] — NOT a generic difficulty claim
- **Page to build:** [URL slug] — [tool / blog / comparison]
- **Cluster covers:** [other keywords merged into this one]
- **Extracted from:** [source URLs]
- **Time to rank:** [estimate, with the reasoning]
```

The "why winnable" line is the one that carries the weight. A named weakness is
verifiable. "Low difficulty" is not.

## 3. `competitor-map.md`

```markdown
## Domains by SERP appearance frequency

| Domain | Appeared in N of M SERPs | Google | Answer engines | Page types | Clusters owned |
|---|---|---|---|---|---|

## URL architecture of the top 3 domains

For each: the slug pattern, how variant pages are structured, hub-and-spoke or flat,
how many pages appear to exist in this topic, and what internal anchor text reveals
about the full cluster map.

## Google-only vs answer-engine-only

- **Both:** [domains] — the strongest competitors
- **Google only:** [domains] — vulnerable to answer-engine displacement
- **Answer engines only:** [domains] — these won citation without ranking; study what
  they did, it is usually cheaper to copy than a ranking play

## What none of them cover

The gap. Feeds directly into the next content brief.
```

## 4. `serps.md`

The working log, appended during Phase 2 and 3. Not a deliverable — a scratch file
that keeps 40 SERPs out of context. One block per query:

```markdown
### [query]

AI Overview: yes/no · Featured snippet: yes/no · Ads: yes/no

| # | URL | Title | Page type | Weak? |
|---|---|---|---|---|

PAA: [questions]
Related: [searches]
```

The `Weak?` column is filled here, at harvest time, while the SERP is in front of
you. Trying to reconstruct it in Phase 7 from a URL list alone is guesswork.

---

## 5. `keywords.xlsx`

Generated by `npm run keywords:xlsx -- <path-to-inventory.csv>`. Never hand-authored
— the column names have to match `app/lib/excel.ts` exactly and the script is the
only thing that guarantees it.

Sheet order matters: `Keywords` (survivors) must be first, because the studio's
parser reads `wb.SheetNames[0]` and ignores the rest.

---

## Reporting numbers honestly

**Report:** unique domains found, total pages fetched, keywords extracted, clusters
after merge, clusters surviving each gate, final shortlist size.

**Do not report** the multiplied slot count (queries × results) as though it were a
count of sites. It inflates the apparent scale of the work and hides the
deduplication that is the actual finding.

Example of an honest summary line:

> 38 long-tails searched → 380 result slots → **47 unique domains** → 34 pages fetched
> → 411 keywords extracted → **156 clusters** after merge → 61 survived the gates →
> **15 shortlisted**.

The collapse from 411 to 15 is not a failure of the run. It is the run working.
