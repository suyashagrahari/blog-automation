## Phase 2 — Gap analysis

**Table stakes** (all pages cover these; the post includes them): what a virtual proposal card
is; personalisation with both names and a photo; sharing over WhatsApp / Instagram; free and
no-signup; the Yes/No button gimmick; a template or design choice.

**The gap.** No page distinguishes a card that is a **file** — an image, PDF or MP4 that lands in
the recipient's gallery — from a card that is a **link** — a hosted page that opens into music, a
countdown and a button that records a reply. mewtrucard.com comes closest: it offers all three
delivery modes on the homepage and says nothing about the tradeoff. That distinction is the post.

**Stale data.** None to supersede, because none of them cite data at all. The closest thing to
staleness is greetings-online.com serving 2022-vintage GIFs beside 2025 ones in the same grid.

**Unanswered questions raised and dropped.** Will the link still work later? Can the recipient
keep it? What happens if the host shuts down? Can it be printed? What if there is no data
connection? Every builder raises "share your link" and resolves none of these.

**Fan-out sub-queries → H2s.**

1. What is a virtual proposal card? → definition H2
2. What formats are there? → "The three formats, and what each one can actually do" (3 H3s)
3. Which should I pick? → "Which format fits which moment" + comparison table
4. What can a link do that an image cannot? → "What a link can do that a file cannot, and what it costs you"
5. Will it last? → "Will the card still be there in ten years?"
6. How do I send it? → "How to send it so it actually lands"
7. When is it a bad idea? → "When a virtual proposal card is the wrong choice"

**Angle.** Wins by being the only post that separates a virtual proposal card you download as a
file from one that opens as a hosted link, prices the tradeoff in both directions using Pew's May
2024 finding that 38% of 2013 webpages are already gone, and grounds the send-it decision in
SubhSandesh's platform-wide 40.0% password-protection rate across 4,524 pages.

## First-party data and the honesty constraint

The post cites ten lines from `content/facts.md` (2026-09-16). **No number is attributed to
proposal pages.** In body prose it says, every time:

- 40.0% password-protection is "platform-wide across all 4,524 pages", not proposal-specific
- 48.9% / 49.1% / 92.9% / 51,164 views are platform totals
- 6.3 hours median first-save-to-last-edit is "sampled on the 'I love you' template, n=1,136, not on proposals"
- 1,094 / 24.2% belongs to `/bouquet-gf`; 1,136 / 25.1% and 16,345 / 31.9% belong to `/love-gf`

The post also states in the send-timing section that **no first-party lead-time data for proposals
exists**, rather than borrowing the Raksha Bandhan n=89 block, which the BRIEF forbids.

Structural limitation carried into `honestAssessment`: the `proposalpages` collection could not be
queried (production-read policy), so no per-template proposal password or lead-time rate is
derivable today. That is the single change that would most strengthen this post.
